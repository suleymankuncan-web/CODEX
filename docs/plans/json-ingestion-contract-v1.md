# JSON Ingestion Contract V1

Date: 6 Mayis 2026

Status: `documented`

Applicability: this generic inbound `POST` draft is not the selected contract
for the company daily pull source. That source is governed by
`docs/contracts/company-daily-kpi-pull-contract-v1.md`. Its stricter no-raw-name,
no-invoice-GUID, previous-day-only, and store-allowlist rules take precedence;
the raw payload and name-review rules below MUST NOT be reused for that source.

## Purpose

Define the future JSON/API ingestion boundary for KPI rows before any endpoint, adapter, scheduler, or external-source client is built.

This contract keeps the current Excel/Power BI path active while making the future API shape explicit enough that an external system can later call HR Axis without bypassing mapping, review, lineage, or idempotency rules.

## Goals

- Accept store and personnel KPI rows without Excel once a real source can call the system.
- Preserve source idempotency across retries, duplicate sends, and operator replays.
- Keep external names, codes, and raw source references traceable.
- Reuse the same canonical import boundary as Excel instead of creating a second scoring path.
- Keep ambiguous store/personnel matches reviewable instead of silently attaching KPI values to the wrong person or store.

## Non-Goals

- Do not build the endpoint in this pass.
- Do not add a fake JSON adapter.
- Do not guess final external field names without a real sample payload or official field list.
- Do not auto-create store or employee master data from KPI rows.
- Do not change KPI scoring, ranking, snapshot, or target logic.
- Do not replace the current Power BI Excel export pilot flow yet.

## Endpoint Draft

```text
POST /api/integrations/kpi-json-import
```

The endpoint draft is intentionally under `integrations` because JSON is another source adapter, not a direct reporting write path.

## Required Envelope

```json
{
  "sourceCode": "external-source-code",
  "periodType": "monthly",
  "periodStart": "2026-05-01",
  "periodEnd": "2026-05-31",
  "idempotencyKey": "external-source-code:monthly:2026-05:export-0001",
  "sourceBatchId": "optional-source-batch-id",
  "rows": []
}
```

Required fields:

- `sourceCode`: identifies the configured integration source, such as `power-bi-kpi` or a future official source.
- `periodType`: `daily`, `weekly`, or `monthly`.
- `periodStart`: inclusive period start date.
- `periodEnd`: inclusive period end date.
- `idempotencyKey`: source-owned stable key for the exact send attempt or export version.
- `rows`: one or more KPI source rows.

Optional but recommended fields:

- `sourceBatchId`: upstream batch/run/export id.
- `sourceGeneratedAt`: upstream generation timestamp.
- `schemaVersion`: source payload schema version.
- `notes`: short operator-visible context for the import batch.

## Row Draft

Rows should carry enough identity and lineage to normalize into canonical KPI actuals:

```json
{
  "sourceRowReference": "sheet:personnel:row-42",
  "scope": "employee",
  "storeCode": "PB_BURSA_MARKA_PARK_AVM",
  "storeName": "Bursa Marka Park Avm",
  "employeeCode": "FM8358",
  "employeeName": "Ayben Oguz",
  "metricCode": "NET_SALES",
  "actualValue": 12345.67,
  "rawPayload": {}
}
```

Required row fields:

- `sourceRowReference`: human-readable source row pointer for reconciliation.
- `scope`: `store` or `employee`.
- `metricCode`: canonical or source-mapped KPI metric code.
- `actualValue`: numeric KPI value.

Identity fields:

- Store rows should include at least one of `storeCode`, `storeExternalRef`, or `storeName`.
- Employee rows should include the store identity plus at least one of `employeeCode`, `employeeExternalRef`, or `employeeName`.
- Name-only rows are accepted only as reviewable candidates; they must not silently create authoritative mappings.

Lineage fields:

- `rawPayload` should preserve the source row object when available.
- `rowHash` is generated by the adapter from the normalized canonical row and source references.
- `sourceRowReference` must be stable enough for an operator to find the upstream row again.

## Idempotency Policy

- `sourceCode + idempotencyKey` identifies one logical import request.
- Re-sending the same `sourceCode + idempotencyKey` with the same payload returns the existing import result.
- Re-sending the same `sourceCode + idempotencyKey` with a different payload is rejected as an idempotency conflict.
- A new upstream export version must use a new `idempotencyKey`.
- Row-level `rowHash` prevents duplicate KPI actuals inside the same logical import.
- Import batch evidence must record whether the request was created, replayed, or rejected as a conflict.

## Matching Policy

Code-based matching wins when present.

Matching order:

1. Exact active external-id mapping for store or employee.
2. Exact source code match, such as store code or seller/employee code.
3. Normalized store name plus normalized employee name inside the same store scope.
4. Review queue when name-only matching is missing, duplicate, stale, or ambiguous.

Store/personnel name matching remains reviewable.

Ambiguous rows go to review.

No source adapter may auto-create store or employee master data.

If a row cannot be matched safely:

- store ambiguity becomes `unmapped_store` or `ambiguous_store`.
- employee ambiguity becomes `unmapped_employee` or `ambiguous_employee`.
- invalid metric/value shape becomes `invalid_metric`.
- period mismatch becomes `invalid_period`.

Rows in review may be fixed by creating or correcting master-data mappings, then replaying the same batch through the normal materialization path.

## Canonical Import Boundary

When JSON becomes real, it must enter through the same canonical import boundary as Excel.

Pipeline:

1. Source adapter
2. Canonical import payload
3. Shared mapping and validation
4. Data quality and lineage
5. Materialization and snapshotting
6. Scoring and reporting

Canonical row fields must include:

- `sourceCode`
- `sourceBatchId`
- `sourceRowReference`
- `rowHash`
- `rawPayload`
- `scope`
- `storeExternalRef`
- `employeeExternalRef`
- `periodStart`
- `periodEnd`
- `metricCode`
- `actualValue`

No source-specific scoring branch is allowed in V1.

## Review And Operator UX

The JSON importer should create the same kind of operator evidence used by Excel import:

- batch id
- source code
- idempotency key
- period
- row count
- valid count
- invalid count
- needs-review count
- promoted/materialized count
- data quality reasons
- sanitized sample rows

Review rows should show:

- source row reference
- raw store/personnel names and codes
- matched candidate if any
- reason code
- required operator action

## Security And Audit Boundary

- Endpoint requires authenticated integration/admin authorization.
- Service credentials or machine-to-machine auth must be designed separately before implementation.
- Raw secrets, tokens, cookies, and private credentials must never be stored in import evidence.
- Every accepted, replayed, rejected, and materialized import must emit audit events with source metadata.

## Open Questions Before Implementation

- Which external system will call this first?
- Will the caller be user-authenticated, service-authenticated, or both?
- What are the official store and employee identity keys?
- Will the source send one metric per row or metric columns per row?
- Will returns/cancellations be represented as negative values, replacement rows, or adjustments?
- What retry and timeout behavior does the caller expect?

## Implementation Gate

Do not implement `POST /api/integrations/kpi-json-import` until at least one of these exists:

- real sample JSON payload,
- official field list,
- external system API documentation,
- signed integration decision that explicitly accepts a first limited schema.
